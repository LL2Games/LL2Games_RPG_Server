# 서버 안정성 개선 상세

## 1. 문서 목적

LL2Games RPG Server를 테스트하는 과정에서 발견한 패킷 처리, 서버 간 인증 및 플레이어 상태 저장 문제와 개선 내용을 정리한 문서입니다.

각 개선 사항은 문제를 재현한 뒤 코드 수정과 회귀·통합 테스트를 통해 검증했습니다.

## 2. 개선 사항 요약

| 영역 | 발견한 문제 | 개선 내용 |
| --- | --- | --- |
| 패킷 처리 | 1 KiB 버퍼 제한과 TCP 수신 경계 처리 부족 | 수신 단위와 최대 패킷 크기 분리, 누적 버퍼 기반 파싱 |
| 서버 인증 | LOGIN·WORLD·CHANNEL 서버에 티켓 검증 없이 접속 가능 | Redis 기반 일회성 인증 티켓 적용 |
| 상태 저장 | 종료 시 일부 스탯만 저장하고 저장 작업이 다른 작업을 지연 | 60초 주기 저장, 종료 스냅샷, 전용 저장 작업 풀 및 트랜잭션 적용 |

## 3. 패킷 수신 규격 개선

### 3.1 발견한 문제

기존 구현은 버퍼 크기와 최대 패킷 크기를 모두 1 KiB로 취급했습니다.

인벤토리의 모든 아이템 정보를 전송하는 테스트에서 패킷이 1 KiB를 초과했고, 임시로 버퍼를 14,096바이트까지 확장했지만 다음 문제가 남았습니다.

- `recv()` 한 번의 결과를 하나의 완성된 패킷으로 간주할 가능성
- TCP 부분 수신과 여러 패킷의 병합 수신 처리 부족
- 수신 버퍼 크기와 프로토콜상 허용하는 최대 패킷 크기의 역할 혼합
- 비정상적으로 큰 길이 헤더를 이용한 메모리 사용 가능성

### 3.2 개선 내용

```cpp
namespace PacketLimits
{
    inline constexpr std::size_t kReceiveChunkSize = 4 * 1024;
    inline constexpr std::size_t kMaxPacketSize = 16 * 1024;
}
```

- `kReceiveChunkSize`: 한 번의 `recv()`에서 읽는 단위
- `kMaxPacketSize`: 프로토콜에서 허용하는 헤더 포함 최대 패킷 크기
- 세션별 수신 버퍼에 데이터를 누적
- 헤더가 부족하면 다음 수신까지 데이터 유지
- 전체 패킷이 부족하면 `NeedMoreData` 반환
- 최소 크기 미만 또는 16 KiB 초과 패킷 거부
- 하나의 수신 데이터에 여러 패킷이 포함된 경우 순서대로 반복 처리
- 헤더 접근 시 정렬되지 않은 포인터 역참조 대신 `memcpy()` 사용

### 3.3 관련 코드

- `SERVER/include/COMMON/packet/Packet.h`
- `SERVER/src/COMMON/packet/PacketParser.cpp`
- `Test/cpp/PacketParserLengthTest.cpp`

### 3.4 검증 항목

- 최대 크기 패킷 승인
- 최대 크기 초과 패킷 거부
- 헤더보다 작은 길이 거부
- 부분 수신 데이터 유지
- 병합된 여러 패킷 순차 처리
- 2바이트 길이 접두사 왕복 처리

### 3.5 남은 한계

16 KiB는 TCP의 제한이 아니라 현재 가장 큰 인벤토리 패킷과 확장 여유를 고려한 프로젝트 프로토콜 정책입니다.

향후 인벤토리 데이터가 더 커질 경우 최대 크기를 계속 늘리기보다 다음 방법을 검토해야 합니다.

- 페이지 단위 전송
- 변경된 슬롯만 전송
- 패킷 종류별 최대 크기 분리

## 4. 일회성 인증 티켓 적용

### 4.1 발견한 문제

기존에는 클라이언트가 LOGIN 서버에서 인증한 뒤 WORLD와 CHANNEL 서버에 접속할 때, 이전 서버에서 정상적인 절차를 거쳤는지 확인할 수단이 부족했습니다.

이 때문에 서버 주소와 패킷 규격을 알고 있다면 중간 인증 절차를 거치지 않고 접속을 시도할 수 있었습니다.

### 4.2 티켓 생성

Linux `getrandom()`을 이용해 32바이트의 난수를 생성합니다.

32바이트는 256비트이며, 각 바이트를 두 글자의 소문자 16진수로 변환해 64글자 티켓으로 사용합니다.

티켓은 서명된 인증서가 아니라 Redis에 저장된 값을 조회하기 위한 추측하기 어려운 일회성 식별자입니다.

티켓 저장에는 다음 Redis 명령을 사용합니다.

```text
SET key value NX EX ttl
```

- `NX`: 같은 키가 이미 존재하면 저장하지 않음
- `EX`: 지정한 시간이 지나면 자동 만료
- 충돌이 발생하면 최대 3회까지 새 티켓 생성
- 티켓 검증에는 `GETDEL`을 사용해 조회와 삭제를 원자적으로 처리

### 4.3 인증 흐름

#### LOGIN → WORLD

1. 클라이언트가 LOGIN 서버에 ID와 비밀번호 전송
2. LOGIN 서버가 MySQL 계정 정보 검증
3. World 티켓 생성
4. Redis에 300초 TTL로 저장
5. 클라이언트에 World 티켓 전달
6. WORLD 서버가 `GETDEL`로 티켓 소비
7. 티켓이 존재할 때만 World 세션 인증 완료

#### WORLD → CHANNEL

1. 클라이언트가 캐릭터와 채널 선택
2. WORLD 서버가 Channel 티켓 생성
3. 티켓 값에 `accountId`, `characterId`, `channelId` 저장
4. Redis에 60초 TTL로 저장
5. 클라이언트에 Channel 접속 정보와 티켓 전달
6. CHANNEL 서버가 `GETDEL`로 티켓 소비
7. 티켓의 `channelId`와 현재 Channel 서버 ID 비교
8. 해당 캐릭터의 종료 저장이 진행 중인지 확인
9. 검증 성공 후 MySQL에서 플레이어 상태 조회

### 4.4 재사용 방지

`GETDEL`은 값을 조회하는 동시에 키를 삭제합니다.

따라서 동일 티켓의 첫 번째 사용은 성공하지만 두 번째 사용은 Redis에서 값을 찾을 수 없어 거부됩니다.

TTL이 지난 티켓 역시 Redis에서 자동 삭제되어 사용할 수 없습니다.

### 4.5 비동기 인증 결과 보호

비동기 인증 작업이 진행되는 동안 연결이 종료되면 운영체제가 동일한 fd를 새로운 연결에 재사용할 수 있습니다.

fd만으로 세션을 확인할 경우 이전 연결의 인증 결과가 새로운 연결에 적용될 수 있으므로 다음 값을 함께 비교합니다.

- fd
- sessionId
- generation
- 세션 종료 상태

현재 세션의 식별자와 일치하지 않는 오래된 인증 결과는 폐기합니다.

- 티켓 길이 64글자 확인

- 한 번의 실행에서 10,000개 티켓 중복 없음
- 최초 Channel 티켓 사용 성공
- 동일 티켓 재사용 거부

### 4.8 남은 한계

## 5. 플레이어 상태 주기·종료 저장

### 5.1 발견한 문제

기존 구현은 게임 종료 시 플레이어 스탯 일부만 저장했습니다.

다음 정보는 종료 후 일관되게 복원되지 않았습니다.

- 현재 맵
- 플레이어 위치
- 캐릭터 스탯
- 인벤토리 메타데이터와 아이템
- 퀵슬롯

또한 종료 저장을 일반 작업 풀에서 수행했을 때 이동 부하 종료 직후 신규 인증이 약 14초 지연되는 상황을 확인했습니다.

종료된 세션의 `Player` 객체를 비동기 저장 작업에서 계속 참조하면 객체 수명 문제도 발생할 수 있었습니다.

### 5.2 변경 감지와 저장 버전

플레이어의 저장 대상 정보가 변경될 때 `MarkSaveNeeded()`를 호출합니다.

```cpp
void Player::MarkSaveNeeded()
{
    m_saveVersion.fetch_add(1);
}
```

- 버전이 `0`: 저장되지 않은 변경 없음
- 버전이 `0`이 아님: 저장해야 할 변경 존재

저장 시작 시 현재 상태와 `saveVersion`을 `PlayerSaveData`에 복사합니다.

DB 저장이 성공한 뒤 현재 버전과 스냅샷 버전이 같을 때만 버전을 `0`으로 변경합니다.

저장 중에 새로운 상태 변경이 발생하면 현재 버전이 증가하므로 비교에 실패하고 변경 상태가 유지됩니다. 해당 상태는 다음 저장 주기에 다시 저장됩니다.

### 5.3 60초 주기 저장

1. 주기 저장 대상 플레이어 확인
2. 변경되지 않은 플레이어는 저장 생략
3. `PlayerSaveData` 스냅샷 생성
4. 일반 작업 풀에 `PlayerSaveTask` 등록
5. MySQL 트랜잭션으로 상태 저장
6. 저장 성공 시 스냅샷 버전과 현재 버전 비교
7. 버전이 같으면 저장 완료 상태로 변경
8. 버전이 다르거나 저장에 실패하면 다음 주기에 재시도

### 5.4 연결 종료 시 최종 저장

1. 세션을 종료 상태로 변경
2. 진행 중인 세션 작업이 끝날 때까지 대기
3. 플레이어를 현재 맵에서 제거
4. 세션과 분리된 `PlayerSaveData` 스냅샷 생성
5. 종료 저장 진행 중인 `characterId`를 별도 집합에 등록
6. `FinalPlayerDataSaveTask`를 전용 저장 작업 풀에 제출
7. DB 저장 실패 시 총 3회까지 시도
8. 저장 완료 후 진행 중인 `characterId` 제거

종료 저장이 완료되기 전에 동일 캐릭터가 다시 인증하면 이전 상태를 조회할 수 있으므로 CHANNEL 인증 단계에서 최종 저장 진행 여부를 확인하고 접속을 거부합니다.

### 5.5 저장 데이터

`PlayerSaveData`에는 다음 정보가 포함됩니다.

- 저장 버전
- 캐릭터 ID
- 맵 ID
- X·Y 좌표
- 캐릭터 스탯
- 인벤토리 메타데이터
- 인벤토리 아이템
- 퀵슬롯

### 5.6 MySQL 트랜잭션

다음 데이터를 하나의 트랜잭션으로 저장합니다.

1. 캐릭터 맵·위치·레벨
2. 캐릭터 스탯
3. 인벤토리 메타데이터와 아이템
4. 퀵슬롯

중간 저장이 하나라도 실패하면 `ROLLBACK`을 실행합니다. 모든 작업이 성공했을 때만 `COMMIT`합니다.

### 5.8 검증 항목

- 변경되지 않은 플레이어 저장 생략
- 상태 변경 후 저장 필요 상태 확인
- 스냅샷 버전 기록 확인
- 저장 중 새로운 변경이 발생했을 때 변경 상태 보존
- DB 실패 후 저장 필요 상태 유지
- 실패한 저장 재시도
- 캐릭터·스탯·인벤토리·퀵슬롯 커밋 확인
- 일부 저장 실패 시 트랜잭션 롤백 확인
- 종료 후 맵·좌표·인벤토리·퀵슬롯 복원 확인

### 5.9 남은 한계

- 60초 주기 저장은 인증·게임 패킷과 일반 작업 풀을 공유
- 종료 저장이 세 번 모두 실패하면 영속적인 재시도 큐가 없음
- 저장 중인 캐릭터의 재접속은 대기시키지 않고 거부
- 프로세스가 즉시 강제 종료되면 작업 풀에 제출된 저장이 완료되지 않을 수 있음

## 7. 테스트 결과 해석

이번 검증으로 다음 사항을 확인했습니다.

- 패킷 경계 입력에서 서버가 비정상 종료되지 않음
- 일회성 티켓의 재사용과 만료 티켓이 거부됨
- DB 일부 저장 실패 시 이전 커밋 상태가 유지됨
- 종료 저장을 전용 작업 풀로 분리한 뒤 부하 종료 후 신규 인증이 정상 처리됨
- 300개 클라이언트의 인증·맵 입장·이동 처리를 완료함

다만 같은 맵의 모든 플레이어에게 이동 패킷을 전달하므로 접속자 증가에 따라 브로드캐스트 비용이 빠르게 증가합니다.

이번 결과는 localhost 기반 단일 서버 검증이며 운영 환경의 최대 수용 인원을 의미하지 않습니다.
